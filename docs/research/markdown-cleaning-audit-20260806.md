# remove_markdown 系统审计（2026-08-06）

对 `cleanText` 里 7 条 markdown 正则做穷举式审计。方法：每条规则准备「该处理 / 不该动 /
畸形」三类输入批量跑，判据是**念出来是不是用户想听的**，而不是「像不像 markdown」。

约 60 个用例 + 真实世界文本（维基链接、Python dunder、算式、文件名），全本地零上游成本。

## 核心认知：`\w` 只是 ASCII，中文不在其中

这是本轮所有修复的基础，也是我**一开始搞错**的地方。

我最初给 `__` 加了 `\w` 边界，却在注释里写「`**` 刻意不加，因为中文没有词边界，加了会打破
中文粗体」。**这是错的** —— 变异测试发现「给 `**` 加边界后测试没变红」，与注释矛盾，查下去：

```js
/\w/.test('重')  // false  —— 中文字符不是 \w
/\w/.test('a')   // true
```

JS 的 `\w` 等价 `[A-Za-z0-9_]`。所以 `\w` 边界对中文强调**零影响**，
`这是**重点**内容` 加边界后依然正确得到 `这是重点内容`。

认知纠正后，`**` 和单 `*` 都能安全加上边界，于是 C 和 C2 从「固有歧义」变成「可修」。
**如果我没去核对那条注释，这两个 bug 会一直留着。**

## 修复详情

### A — `__` 与 `**` 共用正则导致丢失边界保护

原来是 `/(\*\*|__)(.*?)\1/g` 一条管两个符号，于是 `__` 拿不到 `\w` 保护，而**下面单 `_`
那条早就有了** —— 同一份代码对同类输入两种待遇，这不是权衡，是漏了。

实测受害者都是真实文本：

| 输入 | 修复前 |
|---|---|
| `变量 my__temp__value` | `变量 mytempvalue` |
| `常量 MAX__SIZE__LIMIT` | `常量 MAXSIZELIMIT` |

拆成两条，各自加 `(^|[^\w]) ... (?![\w])`。

### B — URL 里的配平括号

`[^)]*` 在**第一个** `)` 就停，剩下的漏出来被念成「右括号」。维基百科链接是最常见来源，
实测 4/4 全残留：

| 输入 | 修复前 |
|---|---|
| `见 [铝](https://zh.wikipedia.org/wiki/铝_(元素))` | `见 铝)` |
| `参考 [Foo](https://en.wikipedia.org/wiki/Foo_(bar))` | `参考 Foo)` |

改用 `\((?:[^()]|\([^()]*\))*\)` —— 「非括号字符，或一整对不含嵌套的括号」。
仍是线性的（每个位置只有一种匹配方式，无可回溯歧义）。只支持一层：CommonMark 的裸 URL 里
两层以上极罕见，无上限需要递归正则。

### C / C2 — 算式与标识符里的星号

| 输入 | 修复前 |
|---|---|
| `结果是 2*3*4` | `结果是 234` |
| `面积 a*b*c` | `面积 abc` |
| `x**2**y` | `x2y` |
| `file**name**.txt` | `filename.txt` |

四条强调规则（`**` `__` `*` `_`）现在**统一**都有 `\w` 边界。

**一处只有端到端验证才能发现的问题**：给 `**` 加完边界后，`x**2**y` 变成了 `x*2*y` ——
被**下游的单 `*` 规则**接手了。修一条正则却被后一条抵消，单测每条正则都看不出来。
所以单 `*` 的边界里还要排除 `*` 本身：`[^\w*] ... (?![\w*])`。

### D — 反引号首尾数量不一致

`` `{1,3}(.*?)`{1,3} `` 允许首尾数量不同，于是 `` `a``b` `` 被贪婪吃成 `` ab` ``。
改用反向引用 `` (`{1,3})([^`]*)\1 `` 要求一致。

**顺带更快**：最坏合法请求的清理耗时从 0.56ms 降到 0.51ms（反向引用无需回溯探测）。

## 明确不修的两项（固有歧义）

### E — `__init__ 方法`

`__init__`（前后都是空格）与真粗体 `__粗体__` 在语法上**无法区分**。CommonMark 也判为强调。
`\w` 边界救不了它，因为两侧确实是空白。

修它需要维护「Python 特殊方法名单」之类的启发式，误伤风险高于收益。

### F — `*.txt 和 *.md`

两个 `*` 中间夹着 `.txt 和 `，与 `*斜体*` 同构。强修会伤到合法斜体。

**这两项都属于「markdown 语法本身有歧义」，不是实现缺陷。** 记录在此，免得后人重复调查。

## ReDoS 复核（本项目最痛的教训）

这个项目曾因 `\[(.*?)\]\(.*?\)` 在 16KB 输入上跑到 **36 秒**（Workers CPU 上限 10ms），
所以每次动这些正则都必须重测复杂度。

针对**新引入**的正则各自构造攻击：

| 攻击形状 | 391KB 耗时 |
|---|---|
| `[a](()` 重复（配平括号） | 4.8ms（混合最坏） |
| `[a](` + 16000 个 `(` | 0.0ms |
| 16000 个反引号 | 0.1ms |
| ` __a` 重复 | 0.3ms |
| `**a` 重复 | 0.2ms |

全部随长度**线性**。最坏合法请求（50000 字符全选项）中位 **0.51ms**。

## 测试

新增 7 项（`test/unit/clean-text.test.mjs`），**逐个验证过对着它所守护的实现会变红**，
含 7 个变异：

- R：`__` 回退共用正则 → 抓到
- S：URL 回退 `[^)]*` → 抓到
- T：反引号回退 `{1,3}` → 抓到
- V：`**` 去掉边界 → 抓到
- W：单 `*` 去掉边界 → 抓到
- X：单 `*` 保留边界但不排除 `*` 本身（相互啃咬）→ 抓到
- U（初版）：`**` 加边界 → **存活**，正是它暴露了我那条错误注释

**U 存活是本轮最有价值的一次「失败」** —— 变异存活通常意味着测试有缺口，但这次意味着
**注释在说谎**。核对下去才发现 `\w` 不含中文，进而修掉了 C 和 C2 两个真 bug。

共 337 项测试（319 fast + 19 e2e），0 失败。
