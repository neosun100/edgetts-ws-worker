# chunks 维度普查（2026-08-06）

延续 P1-6 日志带来的第三个维度。与音色普查不同，**分块行为可以本地穷举**，所以这一轮的
绝大部分测量是零上游成本的：约 8000 次本地 `smartChunkText` 调用，只有边界验证打了生产
（4 次）。

要回答 ROADMAP 里挂着的两个问题：**`MAX_CHUNKS=45` 与默认 `chunk_size=300` 合理吗？**

---

## 结论速览

| 问题 | 答案 |
|---|---|
| 默认 `chunk_size=300` 的实际容量？ | **12179–13500 字符**（随文本形态），README 原写「约 13500」偏乐观 |
| 跑满 50000 字符需要多大 `chunk_size`？ | **≥1125**（最坏形态 1150），此前**文档完全没说** |
| `MAX_CHUNKS=45` 合理吗？ | **合理**。它由平台的 50 subrequest 硬限决定，留 5 个余量给 token/语音列表 |
| 默认 `chunk_size=300` 合理吗？ | **合理但可议**：13500 字符覆盖绝大多数用例，且首字节最快；需要更长文本时由 413 引导 |
| 发现的缺陷 | **413 文案宣称一个自相矛盾的容量** —— 已修，见下 |

## 一、`chunk_size` → 最大字符数（本地二分，实测）

| `chunk_size` | 中文密标点 | 英文散文 | 无标点英文 | 说明 |
|---|---|---|---|---|
| 300（默认） | 13500 | **12179** | 13500 | 英文散文最吃亏 |
| 500 | 22478 | 22279 | 22500 | |
| 1125 | 50000 | 50000 | 50000 | 刚好跑满硬上限 |
| 2000（上限） | 50000 | 50000 | 50000 | 有余量（26 块） |

**50000 字符（`MAX_INPUT_CHARS`）在各 `chunk_size` 下的分块数**（`!` = 超 45 被拒）：

| `chunk_size` | 中文密标点 | 中文长句 | 英文散文 | 无标点英文 |
|---|---|---|---|---|
| 50 | !1011 | !480 | !1112 | !1000 |
| 300 | !167 | !80 | !186 | !167 |
| 1000 | !51 | 24 | !51 | !50 |
| **1200** | 42 | 20 | 43 | 42 |
| 2000 | 26 | 12 | 26 | 25 |

跑满 50000 所需的**最小 `chunk_size`**：中文长句 533、中文密标点 1112、无标点英文 1112、
**英文散文 1125（最大）**。纯数学下界是 `ceil(50000/45) = 1112`，差距来自标点提前收尾。

**线上边界验证**（英文散文，50000 字符）：

```
chunk_size=1124  ->  HTTP 413  too_many_chunks
chunk_size=1125  ->  HTTP 200  19281168B  17.06s
chunk_size=2000  ->  HTTP 200  19269936B  17.21s
```

本地预测与生产**逐字符吻合**。

## 二、填充率不是常数，而是量化效应

「实际平均块长 / 名义 `chunk_size`」：

| 文本形态 | @50 | @300 | @1000 | @2000 |
|---|---|---|---|---|
| 中文密标点 | 99% | 100% | 95% | 91% |
| 中文长句（无标点） | 100% | 100% | 100% | 100% |
| 英文散文（44 字符句） | 88% | 90% | 95% | 91% |
| 82 字符句 | **65%**（@125） | — | — | — |

**关键发现**：填充率**不能用一个系数近似**。当 `chunk_size` 略小于句长的整数倍时，每块都会
浪费接近一整句 —— 82 字符句在 `chunk_size=125` 下只能装 1 句（81/125 = 65%）。

这直接否掉了我最初的修法（见下）。

## 三、修掉的缺陷：413 文案宣称一个自相矛盾的容量

**旧文案**（50000 字符 + `chunk_size=1124` 被拒时）：

> 文本过长：按 chunk_size=1124 会切成 46 个分块，超过上限 45。
> **当前 chunk_size 下最多约 50580 字符**；调大 chunk_size（上限 2000）可处理更长文本。

**自相矛盾**：这条请求只有 50000 字符却被拒，而文案说 50580 可行。

根因：`45 × chunk_size` 是**乘积上界**，只有每块填满才成立。而且 `MAX_INPUT_CHARS=50000`
是先于分块的硬上限，所以任何 >50000 的数字都不可能达到 —— **这正是 v2.20.0 在 README 里修掉
的「90000 字符不可达」同一类错误，当时改了文档、没改错误文案。**

**新文案**：

> 文本过长：按 chunk_size=100 会切成 至少 500 个分块，超过上限 45。
> **这段文本（50000 字符）请把 chunk_size 调到约 1125 以上**（上限 2000）；块越粗则上游调用越少。

用**二分实算**，不估。成本 1.54ms（中位），只在已经要返回 413 的路径上跑，且不打上游。

### 为什么不用系数估算 —— 试过，不行

`ceil(len/45)` 乘系数，对 88 个（字符数 × 文本形态）组合逐一验证：

| 系数 | 结果 |
|---|---|
| 1.05 | ✗ 10 例失败 |
| 1.15 | ✗ 4 例失败 |
| 1.25 | ✗ 3 例失败 |
| 1.4 | ✗ 1 例失败 |
| 1.6 | ✗ 1 例失败 |

**没有一个系数全通过。** 因为填充率是量化效应而非常数（见上）。所以改用二分。

二分的前提是**分块数随 `chunk_size` 单调不增** —— 已验证：4 种形态 × `chunk_size` 50→2000
逐值扫描共 **7800 个点，0 次违反**。向上取整到 25 的倍数后仍可行：**44/44 通过**。

### 闭环验证：照建议改就能过

| 文本形态 | 拒绝 | 建议 | 重试结果 |
|---|---|---|---|
| 英文散文 | 413 | 1125 | ✅ 200 |
| 82 字符句 | 413 | 1150 | ✅ 200 |
| 极短句 | 413 | 1125 | ✅ 200 |
| 中文密标点 | 413 | 1125 | ✅ 200 |

## 四、`MAX_CHUNKS=45` 与默认 `chunk_size=300` 是否合理

**`MAX_CHUNKS=45`：合理，不建议改。** 它不是拍的数字 —— Cloudflare Workers 单次调用最多 50
个 subrequest，留 5 个给 token 端点与语音列表。调大会撞平台硬限（线上实测过：51 块即 500）。

**默认 `chunk_size=300`：合理但有取舍。**

- ✅ 覆盖 12179–13500 字符，绝大多数用例够用
- ✅ 首字节最快（流式场景第一块最先返回）
- ⚠️ 超过约 12000 字符就要调参，而**此前文档没说该调到多少** —— 这是真正的痛点，
  已由新 413 文案 + README 表格解决
- 不建议改默认值：调大会让流式首字节变慢，而受影响的只是少数长文本用户，
  他们现在能从错误信息里直接拿到该用的值

## 复现方式

```bash
# 本地穷举(零上游调用)
node -e 'import("./src/worker.js").then(({__test__})=>{ /* 见下方脚本 */ })'
```

本轮的本地探针是一次性脚本（未落库，因为 `smartChunkText` 的行为已由
`test/integration/limits-and-failures.test.mjs` 里的两个新测试钉住）：

- `the too_many_chunks message suggests a chunk_size that actually works` ——
  12 个（形态 × 长度）组合，每个都验证「拒绝 → 按建议重试 → 200」闭环
- `chunk count decreases monotonically as chunk_size grows` —— 守护二分的前提

**测试设计上的一处自纠**：这两个测试的第一版只用 50000 字符输入，结果**把「1.05 系数」这个
错误实现放过了**（变异测试发现）。那个系数在 **5000 字符**处才失效 —— 短输入才是有区分力的
用例。加入 5000/20000 两个长度后，变异被抓到。
**教训：参数化测试要覆盖参数空间里「机制会改变」的那一段，不只是极值。**
