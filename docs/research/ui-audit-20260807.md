## 唯一真缺陷：6 个控件缺正式可访问名称

18 个可见表单控件里有 6 个既无 `<label>` 关联、也无 `aria-label`：

| 控件 | 原状 | 后果 |
|---|---|---|
| 语言/地区/性别 筛选 `<select>` ×3 | **连 placeholder 都没有** | 读屏只念当前值「全部语言」，用户不知道这是什么筛选 |
| 音色搜索框 | 仅 placeholder | placeholder 获得焦点后消失 |
| 停顿时长 `<input type=number>` | 仅 placeholder | 同上 |
| 输出格式 `<select>` | 有可见 `<label>` **但缺 `for`** | 与前几轮修滑块 label 时同一个问题 |

判据刻意**不接受 placeholder 兜底**：它在获得焦点后通常消失，规范上也不是可访问名称的
正当来源。

已修：三个筛选与搜索、时长用 `aria-label`（它们没有可见标签），输出格式补 `for`/`id`
（它有可见标签，补关联才是正解）。修复后 **18/18 全部有正式名称**。

## 4 次假警报

### 1. AudioContext 采样率不一致 → 无害

代码有两处创建 AudioContext，且**采样率不同**：

- `ensureAudioContext()`（声纹用）→ 硬件默认，实测 **48000 Hz**
- 流式路径 → 显式要求 **24000 Hz**（EdgeTTS PCM 就是 24kHz）

两处都用 `if (!this.audioContext)` 守卫，所以**谁先跑谁赢**。而 PCM 解码用
`createBuffer(1, n, 24000)` 硬编码 24000 —— 看着像典型的「变调/变速」bug。

**实测否掉了**：`AudioBuffer` 自带 `sampleRate`，Web Audio 播放时按 buffer 自己的采样率
重采样。48kHz 与 24kHz 两种 context 下，同一个 buffer 的 `duration` **都是 1.0s**。
不会变调，不是缺陷。

### 2. RAF / objectURL 泄漏 → 不存在

计数不对称看着可疑：`requestAnimationFrame` 7 处 vs `cancelAnimationFrame` 2 处、
`createObjectURL` 3 处 vs `revokeObjectURL` 1 处。两个 RAF 循环靠 `running` 标志自终止，
而 3 处 `running = false` **都不在 `finally` 里** —— 理论上异常路径会泄漏。

实测 7 轮循环（3 轮成功流式 + 3 轮失败请求 + 基线）后三个指标全部稳定：

| 指标 | 基线 | 3 轮成功后 | 3 轮失败后 |
|---|---|---|---|
| 空闲 1.2s 内 RAF 触发 | 0 | 0 | 0–1 |
| objectURL 净值 | 0 | 1 | 0 |
| AudioContext 数 | 0 | 1 | 1 |

objectURL 净值恒为 1 正是设计意图（当前可下载的那一个）；AudioContext 复用不重建。

过程中我还写错过两版探针：先让 `fetch` 抛（发生在 RAF 循环**启动之前**，测不到），
再让 `reader.read()` 抛（`rafCount=1` 是「注册了但回调没来得及触发」，不是循环在跑）。
最后改成**测可观测的资源累积**才得到有效结论。

### 3. XSS「1 个注入元素」→ 是页面自己的 `<script>`

6 个载荷 × 4 个字段，脚本执行 **0 次** —— 但我的探针报「DOM 里出现 1 个注入元素」。

查证：在**干净页面**上运行同一个选择器 `script:not([src])`，也是 1 个 —— 命中的是
Vue 应用本体那段内联 `<script>`。与注入无关。

### 4. 浅色主题「17/25 元素对比度不足」→ 探针忽略了 alpha

报出 `API Key` 标签对比度 **1.00:1**（意味着前景背景完全同色，文字根本看不见）。
这个数字本身就荒谬。

截图是权威证据：**浅色主题完全可读**，深字浅底。

原因：我的探针往上找背景时取了第一个非透明值 `rgba(30,41,59,0.55)` —— 一个**半透明**
深色覆盖层 —— 却**忽略了 alpha 通道**。它叠在 `rgb(240,253,250)` 上实际渲染成
`rgb(124,136,145)`，真实对比度 4.03:1（而非 1.00）。

> 附注：4.03 略低于 WCAG AA 的 4.5，但这是我手算的近似值，且截图观感清晰，
> 不足以据此改设计。若要认真做对比度合规，应当用 Chrome DevTools 的
> Accessibility 面板或 axe-core，而不是手算。

### 附带：roving tabindex 被误报成「键盘不可达」

`voice-item` 的 `tabIndex` 是 `[-1, -1, -1, 0]`，我初版报「3 个元素键盘不可达」。
**那正是 WAI-ARIA radiogroup 的标准实现**：只有当前项进 Tab 序列，组内移动交给方向键。
实测聚焦可行、方向键可移动。

这一条特别值得固化成测试 —— 因为「把 tabindex 全改成 0」看着更可访问，实则会让
322 个音色各占一个 Tab 停留点，键盘用户要按几百次才能走出这个组。已加测试拦住这种"改进"。

## 方法论：假警报的共同模式（连续两轮一致）

上一轮（全模块审计）1 真 : 4 假，这一轮也是 1 真 : 4 假。共同模式仍然是：

**为了验证 X，我手写了一个 X 的实现，然后信了它。**

- 手写 XML 良构检查器 → 处理不了带 `/` 的引号属性值
- 手写 EBML 字节扫描器 → 撞到音频负载里的巧合字节
- 手写对比度计算器 → 忽略 alpha 合成
- 手写「注入元素」选择器 → 命中页面自己的 script
- 手写 RAF 泄漏探针 → 测在了循环启动之前

**有效的判据顺序**：
1. **可观测的最终结果**（截图、资源累积、时长）优于中间量推断
2. **标准工具**（`xml.etree`、`ffprobe`、DevTools a11y 面板）优于手写检查器
3. **被测代码自己的解析器**优于我另写一个
4. **荒谬的数字就是探针错了的信号**（1.00:1、1.65e19）
5. **「通过」也要看是不是空洞的**（0 元素上的 `every()` 恒为 true）
